# 应用是原子的，运行中的请求保留自己的快照

[English](0003-apply-is-atomic.md) | **简体中文**

一个请求会在好几处读配置：准入、重试规划、价格档位、超时，以及最终结算这次尝试的价格。
改动如果落在其中两次读取之间，请求就可能按一个当初没准入它的价格结算，或者把一次尝试
路由到一家已经不存在的 provider。所以一次应用会发布一份新的不可变运行时快照，旧快照则
活到最后一个持有它的请求结算为止。池子的实时状态 —— 闸门、粘性会话绑定、在途占用、限速窗口
—— 是原地调和而不是重建：`Reservation` 里握着池子的克隆，换掉池子就会把真钱花销结算进
一个被丢弃、永远到不了账本的对象。校验和构建替换快照都发生在写文件之前；失败则什么都不
变。会重新接线进程的设置（`listen`、`db_path`、`max_body_bytes`）仅重启生效，应用时
会点名拒绝。

## 考虑过的选项

- 应用前先排空：更简单，但一次重新加载可能一直卡到流量停下为止 —— 而那恰恰是最需要它
  的时候。
- 整体换掉 `Gateway`：reservation 会对着旧池子结算，新池子却在服务下一个请求，在途占用和
  花销就对不上。

## 后果

- HTTP 层通过请求作用域的快照读配置，而不是引用网关的字段；快照覆盖不到的接缝（价格、
  探测、调度、池策略）由网关提供内部可变性。
- 被移除的账号会退役：它不再接新工作，最后一笔尝试结算后就消失；账本行保留。
